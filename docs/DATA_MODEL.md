# Backend data model contract

This is an integration specification for the existing Vellure backend, not a migration to run against it. Align IDs and field names with the existing schema. `src/platform/entities.ts` and `domain.ts` define corresponding frontend DTOs; never expose every persistence field to a browser.

## Common conventions

UUID/opaque IDs as primary keys; UTC `timestamptz`; required `created_at`, `updated_at`, optimistic `version` on mutable entities. Integer paisa with currency `INR`, nonnegative monetary values unless a signed journal amount is explicitly intended. Every tenant-owned record has `vendor_id`. Use composite unique `(vendor_id,id)` targets and composite foreign keys for tenant relationships so a record cannot reference another vendor’s branch/staff/catalog. Index foreign keys and common tenant/date/status list predicates. Financial, history and audit records cannot be deleted by application roles. Archive catalog content instead of cascading deletion into historical transactions.

Localized name/description data is `{en,hi}` (or translation tables if existing backend uses them). English name required; Hindi nullable until translated. Store country `IN`, branch timezone `Asia/Kolkata`, coordinates with latitude/longitude checks. Use PostGIS geography + GiST for radius queries; branch service areas are polygons or explicit radius definitions.

## Lifecycle enums

- Vendors: DRAFT → SUBMITTED → UNDER_REVIEW → APPROVED / CHANGES_REQUESTED / REJECTED; approved vendors may become SUSPENDED / BLOCKED. Backend defines allowed recovery paths. All transitions have actor/reason/history/audit.
- Appointments: PENDING, CONFIRMED, CHECKED_IN, IN_PROGRESS, COMPLETED, CANCELLED, NO_SHOW, REFUNDED. Refund is contingent on money state; do not expose arbitrary state setting.
- Orders: NEW, ACCEPTED, PREPARING, READY, DISPATCHED, DELIVERED, CANCELLED, REFUNDED.
- Inventory transactions: STOCK_IN, STOCK_OUT, SALE, RETURN, ADJUSTMENT, TRANSFER.
- Payouts: PENDING, PROCESSING, PAID, FAILED, HELD, CANCELLED.
- Roles: SUPER_ADMIN, OPERATIONS_ADMIN, FINANCE_ADMIN, SUPPORT_AGENT, CONTENT_MANAGER, MODERATOR. Effective granular permissions are backend-resolved, not inferred from a role label in the UI.

## Data exposure

API projections must exclude password hashes, raw bank details, identity documents and unnecessary customer contact details. Financial history stores snapshots so renamed/deleted catalog records and future pricing changes do not rewrite history. Audit old/new values must be redacted before persistence. Enforce retention and access policy centrally; do not copy customer data to browser local storage.
